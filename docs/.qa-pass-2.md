## BLOCKERS

### B1. The telemetry-gap paragraph asserts a client capability that does not exist — and the fix it implies would recover nothing.

**Location:** lines ~700–710 (§`health-backend-foods-db`, "Telemetry gap,
verified 2026-08-21") and the restatement in §`health-status` → Open / pending
("Client-side scan telemetry is dropping…").

**The claim:** *"What is lost is the client-only terminal outcomes — `ai_label`,
`ai_front`, `usda`, `user_manual` — and all text-query telemetry."*

**Why it is wrong.** The client never sends those outcomes, authenticated or
not. `conjure.logScanAttempt` has exactly three call sites in `src/`, all inside
`lookupBarcode`:

- `src/features/foods/foodSearch.ts:79` — `resolvedFrom: "our_db"`
- `src/features/foods/foodSearch.ts:93` — `resolvedFrom: "off"`
- `src/features/foods/foodSearch.ts:103` — `resolvedFrom: "miss"`

Those are precisely the three outcomes the server already writes for itself
(`ConjureOS/supabase/functions/health-foods-db/index.ts:189` `our_db`, `:218`
`off`, `:229` `miss`). Nothing in `src/` ever passes `ai_label`, `ai_front`,
`usda` or `user_manual`, and nothing ever passes the `query` field — even though
the client SDK type supports all of them
(`src/features/foods/conjureHealthDb.ts:248-252`) and the server accepts them
(`index.ts:455` `allowed = ["our_db","off","usda","ai_label","ai_front","user_manual","miss"]`).
`searchFoods` (`foodSearch.ts:157-192`) contains no telemetry call at all.

**Net:** when the auth-gated `logScanAttempt` 401s, **nothing distinctive is
lost** — the dropped rows duplicate server-side ones. The real gap is the
opposite and larger: AI-parse, USDA and text-search outcomes are **not
instrumented anywhere**, client or server, so the "store every miss" data-
licensing premise (§`health-decisions-other`, 2026-06-25) covers barcodes only,
permanently, and fixing the minted-token escalation would not change that.

**Should say:** "`logScanAttempt` is auth-gated and silently drops on mobile and
when signed out (`conjureHealthDb.ts:64`, `index.ts:97`, `:90`), but its only
callers are the three barcode outcomes the server already records itself
(`foodSearch.ts:79/93/103` vs `index.ts:189/218/229`), so the drop costs
nothing today. The genuine gap is that no code path — client or server — ever
logs an `ai_label` / `ai_front` / `usda` / `user_manual` outcome or a text
query, so provider hit-rate data exists for barcodes only."

**Why blocker:** it is a factual claim about what a shipped data-collection
feature captures, stated twice including in the Open/pending list a maintainer
would work from, and it misdirects the remediation (fix the auth → still no AI
or search telemetry).

### B2. Every published build runs USDA text search on the shared `DEMO_KEY` (30 req/hr per IP). The doc never says so, and lists text search under "Shipped and working".

**Location:** §`health-status` → Shipped and working, line ~1523
(*"**Text search hits Open Food Facts + USDA only** (`foodSearch.ts:157`),
US-biased, per-provider timeouts, progressive paint"*), §`health-food-lookup-chain`
(whole "Text search" block), and §`health-build-publish` → The publish workflow,
which enumerates exactly what CI bakes in.

**Evidence:**
- `src/features/foods/usda.ts:17` — `const KEY = import.meta.env.VITE_USDA_API_KEY ?? "DEMO_KEY";`
- `src/features/foods/usda.ts:5-6` (the file's own header) — *"Free API; ships
  with DEMO_KEY (**30 req/hr per IP**). Set `VITE_USDA_API_KEY` for the 1000/hr
  signup limit."*
- `.github/workflows/publish-store.yml` sets **only** `VITE_SUPABASE_URL` and
  `VITE_SUPABASE_ANON_KEY` (`:52-53` dev, `:59-60` prod). `grep -n "VITE_" `
  returns those four lines and nothing else — **`VITE_USDA_API_KEY` is not baked
  into either the dev or the prod store build.**
- USDA is the *primary* half of the ranked merge, pulled at `0.7 × limit` and
  front-loaded 2:1 (`foodSearch.ts:167`, `:172` `mergeUsFirst(usdaResults, offResults, 2, 1)`, helper at `:137`), and
  it is the provider the app relies on for whole foods; OFF skews branded
  (`usda.ts:2-3`).

So in the app users actually run, the USDA half of text search shares a global
demo quota across every ConjureOS user behind a given IP, and degrades to an
empty list on 429 (the provider `.catch(() => {})` at `foodSearch.ts:187`) with
no user-visible signal.

**Should say:** in §`health-food-lookup-chain` and again in the status list —
"USDA search runs on USDA's shared `DEMO_KEY` in every published build
(`usda.ts:17`; `publish-store.yml` bakes only the two Supabase vars), i.e. 30
requests/hour per IP, silently returning nothing above that. Setting
`VITE_USDA_API_KEY` in the workflow raises it to 1000/hr and is the single
cheapest fix in the food chain."

**Why blocker:** the doc's core obligation is shipped-vs-actual. This is a
headline feature listed flatly as working that is materially degraded in every
build a user can install, and the doc's own build section — which is careful and
correct about the two vars it does document — is where a reader would notice the
omission and doesn't.

## SIGNIFICANT

### S1. Contribution to the community catalog is automatic, unconditional and uid-linked. The App Review section never says so.

**Location:** §`health-cross-app` → "Health data and App Review" (lines
~905–925), which states what the DB stores but not what leaves the device or on
what consent; §`health-food-lookup-chain` (the "Looks wrong?" paragraph), which
says only *"Saving a correction submits only the user's own numbers."*

**Evidence:**
- `src/components/EditableNutritionPreview.tsx:101-110` — `onSave` calls
  `contribute({ food, source, aiConfidence, userEdited })` **unconditionally**
  on every save. There is no opt-in, opt-out, or per-save toggle anywhere in the
  component (grep for `contribute` in `src/` returns only this call site and the
  SDK).
- The failure copy at `:118-120` (*"We couldn't share your edit with the
  community this time"*) confirms sharing is the default, not an election.
- The payload is the full food row — name, brand, barcode, 24 nutrient fields
  (`conjureHealthDb.ts:192-224`).
- The server stamps identity: `index.ts:393` `contributed_by: userId`.
- Consent asymmetry: `call()` uses `getAccessToken()` when available and only
  falls back to a minted token for `WRITE_ACTIONS`
  (`conjureHealthDb.ts:64`, `:75-78`). So **desktop contributes under the user's
  Supabase session with no prompt of any kind**; the one-time ConsentSheet the
  doc cites (2026-07-16 decision) exists only on the mobile minted-token path.

Mitigating and worth stating: `display_attribution` defaults **false**
(`090_health_foods.sql:101`) and the public view nulls `contributed_by` unless
it is set (`090:299`, `index.ts:570-572`), so contributors are not exposed
publicly.

**Should say:** in the App Review section — "Every food a user saves through the
AI-review / 'Looks wrong?' screen is uploaded to the shared catalog
automatically (`EditableNutritionPreview.tsx:103`) and stored against their user
id (`index.ts:393`); there is no per-save opt-out and, on desktop, no consent
prompt at all — the mobile ConsentSheet is a consequence of the minted-token
path, not a contribution consent. Rows are food catalog data, not diary
entries, and `display_attribution` defaults false so the public view strips the
contributor (`090:101`, `:299`). If App Review or a privacy label asks 'what
leaves the device', this is the answer."

**Why significant:** the mandate names cross-app / outbound health data as the
highest-scrutiny path, and this is the one outbound path the doc describes
without describing its consent model.
