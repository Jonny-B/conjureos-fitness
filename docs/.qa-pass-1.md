# QA pass 1 — adversarial review of `docs/CONJURE_HEALTH_INTERNALS.md`

Reviewed 2026-08-21 against `conjureos-fitness` @ `75e8a8b` (doc commit; code at
`eacf65f`, 1.23.1), `ConjureOS` working tree, `conjureos-mobile` working tree,
`conjureos-app-recipes` working tree. Doc NOT edited.

Overall: this is an unusually honest document. Its headline "not shipped" calls
(check-off home, Tell-coach bar, safety layer 3, `notify`) are all **true** and
independently reproduced below. The failures are concentrated in four places:
one internal contradiction that reads as planned-described-as-shipped, one
unsupported platform-security claim, and two overstatements about the mobile
health path.

## BLOCKERS

### B1. §`health-status` claims text search hits the community food DB. It does not.

**Location:** line 1524–1525, "Shipped and working" →
*"text search (community DB + USDA + Open Food Facts, US-biased, per-provider 7s
timeouts, progressive paint)"*

**What is wrong:** the doc contradicts itself and the code. Its own
§`health-food-lookup-chain` (lines 466–470) says, correctly:

> **Gap, verified 2026-08-21:** text search does **not** query the community food
> DB. `conjureHealthDb.searchText()` exists … but nothing in `src/` calls it.

**Evidence:** `src/features/foods/foodSearch.ts:157` `searchFoods` fans out to
exactly two providers — `off.searchText` (`foodSearch.ts:175`) and
`usda.searchText` (`foodSearch.ts:182`). `conjure.searchText` has zero call
sites outside its own definition (`src/features/foods/conjureHealthDb.ts:154`);
grep across `src/` returns only `off`/`usda` uses. The community catalog is
barcode-only (`foodSearch.ts:71` `conjure.lookupBarcode`).

**Should say:** "text search (USDA + Open Food Facts, US-biased …). The
community DB is **barcode-only** — `searchText()` is written but unwired."

**Why blocker:** the status section is the part a returning developer reads
first, and it is the one place in the doc that asserts a capability the code
does not have. It also inflates the perceived value of the `health_foods`
catalog.

### B2. §`health-backend-foods-db` asserts `verify_jwt = false` for `health-foods-db`. The repo says otherwise.

**Location:** lines 567–570, *"`verify_jwt` is intentionally **OFF** at the
platform layer so anon lookups can be served."*

**What is wrong:** there is no evidence for this in the repo, and the repo's own
convention says the opposite.

**Evidence:**
- `ConjureOS/supabase/config.toml:1-3` — *"Functions not listed here keep CLI
  defaults (`verify_jwt = true`), which is what every existing function relies
  on."*
- `config.toml` lists exactly seven functions: `stripe-webhook` (:8),
  `usda-proxy` (:17), `recipes-db` (:25), `mint-app-token` (:34),
  `cleanup-issue-attachments` (:45), `submit-report` (:55), `send-email` (:62).
  **`health-foods-db` is absent.**
- `ConjureOS/.github/workflows/supabase-functions.yml:77` deploys with plain
  `supabase functions deploy "$fn" --project-ref …` — no `--no-verify-jwt`.
- The directly comparable function, `recipes-db`, uses the *same* minted-token
  pattern and *is* declared `verify_jwt = false` (config.toml:25-26) precisely
  because "the gateway JWT check would be wrong here."

**Second-order consequence the doc should be checking:** the doc's own
§`health-backend-foods-db` auth model and §`health-decisions-other` (2026-07-16)
both say the mobile write path presents a **minted ES256 ConjureOS identity
token** (`supabase/functions/health-foods-db/index.ts:125-137`). That token is
not a Supabase JWT. With gateway verification ON it is rejected *before*
`currentUserId()` runs — i.e. the 1.5.1 "mobile contributions now land" fix
would still be dead, and the client would never know, because
`conjureHealthDb.call()` fails open (`conjureHealthDb.ts:88` returns `null` on
any non-`ok`). Anon *reads* would still work either way, since the client sends
`authorization: Bearer <ANON>` (`conjureHealthDb.ts:83`) and the anon key is a
valid Supabase JWT — which is why nothing looks broken.

**Should say:** either (a) "`health-foods-db` is **missing** from
`supabase/config.toml`, so it deploys with the CLI default `verify_jwt = true`;
this is a suspected live bug for the minted-token write path — verify against
the deployed function before trusting mobile contributions", or (b) if the flag
really was flipped by hand in the dashboard, say so explicitly and note that the
repo does not encode it.

**Why blocker:** it is a security-posture claim about an auth gate, stated as
settled fact, contradicted by the only config file in the repo that governs it.

### B3. §`health-mobile-healthkit` describes Gate 2 as unconditional. In code it is conditional and fails OPEN.

**Location:** lines 941–943, *"**Gate 2** — per-(app, permission) user grant,
the same Allow-once / Always / Block trichotomy as the other `native.*` ops."*

**Evidence:** `conjureos-mobile/src/bridge/handlers.ts:318` —

```ts
// Gate 2 — per-(app, permission) user grant (same trichotomy as native.*).
if (ctx.grants) {
  const stored = await ctx.grants.get(appSlug, "native.health");
  …
}
// Gate 3 — the OS HealthKit / Health Connect auth …
return ctx.healthOps(op, payload);
```

`grants` is declared **optional** on the handler context
(`handlers.ts:114` `grants?: GrantsStore;`). If it is absent, the entire consent
gate is skipped and control falls straight through to `healthOps` — the health
read proceeds with no user grant, gated only by the manifest declaration
(Gate 1) and the OS sheet (Gate 3).

**Mitigating fact, stated for accuracy:** the shipped path does pass it —
`src/host/Runner.tsx:412` and `:420` both supply `grants: kernel.grants`. So
this is a latent structural weakness, not a live bypass on today's build.

**Should say:** "Gate 2 is wrapped in `if (ctx.grants)` (handlers.ts:318) and
therefore **fails open** if the context is ever constructed without a grants
store; `grants` is optional on `HandlerContext` (handlers.ts:114). Today's
Runner always supplies it (Runner.tsx:412/420), so the gate holds in practice —
but do not describe it as unconditional, and do not construct a handler context
without grants."

**Why blocker:** the mandate's highest-scrutiny path. This section is quoted
into external developer docs and bears on Apple 4.7.1 / 5.1 review; an
"unconditional consent gate" claim that the code does not guarantee is exactly
the wrong thing to have in writing.

### B4. The mobile health path is behind a build flag the doc never mentions; the prescribed verification loop cannot run.

**Location:** §`health-mobile-healthkit` (whole section, esp. lines 935–952),
§`health-overview` line 58–60, §`health-status` line 1533–1534
(*"Apple Health / wearable exercise calories added back to the day's budget"*
listed flatly under **Shipped and working**).

**What is missing:** HealthKit / Health Connect is compiled in only when
`EXPO_PUBLIC_CONJUREOS_HEALTH === "1"`.

**Evidence:**
- `conjureos-mobile/app.config.ts:22` — `const health = process.env.EXPO_PUBLIC_CONJUREOS_HEALTH === "1";`
- `app.config.ts:93` — `if (health) { … "@kingstinct/react-native-healthkit" … "react-native-health-connect" … }` (plugins added only under the flag).
- `conjureos-mobile/eas.json:40` — `"EXPO_PUBLIC_CONJUREOS_HEALTH": "1"` appears **only** in the `testflight` profile. The `development` (eas.json:7) and `preview` (eas.json:20) profiles do not set it.
- With the module absent, `loadHK()` (`src/native/healthOps.ts:37-49`) returns
  null and `available` reports `platform: "unsupported"` (`healthOps.ts:390`).

So a `npx expo run:ios` dev client — the loop `conjureos-mobile/CLAUDE.md`
prescribes for real verification — **cannot exercise HealthKit at all**, and the
`testflight` profile is all-prod, so reaching it requires a dev→main promotion.

**Should say:** a subsection stating the flag, which profiles carry it, that
dev/preview clients report `unsupported`, and that verifying a Health change
end-to-end currently requires a TestFlight build (owner-approved spend per
`conjureos-mobile/CLAUDE.md` → Deploys). §`health-status` should qualify wearable
calories as "shipped, but only reachable on the TestFlight/prod mobile build."

**Why blocker:** a reader takes "Apple Health calories are read in" as a working
feature on any mobile build, and takes the three-gate description as testable.
Neither is true on the builds a developer can make.

### S4. The VFS decision's central justification is undercut by the doc's own persistence section, and the two are never reconciled.

§`health-decision-vfs-not-supabase` (lines 1357–1359) rests point 1 on:
*"**Phase 9 platform sync already backs up VFS files.** So 'put it in the VFS'
is not 'don't back it up'."*

But §`health-persistence-split` (lines 388–395) establishes — correctly — that
`localStorage` (`conjure-fitness:store:v2`) is **authoritative** and **"not part
of ConjureOS cloud file-sync"**, and VFS `store.json` is a best-effort mirror
*never read back as authoritative once a device-local copy exists*.

**Evidence:** `src/data/mockRepository.ts:52` `LOCAL_KEY`,
`mockRepository.ts:170-177` (init: local copy wins, VFS deliberately not
consulted), `mockRepository.ts:192-196` (`flush()` writes both).

Net: the authoritative copy of plan / day-log / workout-session data is
**unsynced**, so the backup rationale that justified the decision no longer
holds in the form stated. The doc mentions the trade-off ("cross-device
propagation is seed-on-first-run") but never says the sync-backup premise of the
decision has been eroded by a later fix.

**Should say:** in the decision section, a note — "the sync-backup premise was
later weakened: `localStorage` became authoritative and is not synced, so the
VFS mirror is a seed, not a live backup. The decision still stands on points 2
and 3 (no new Supabase surface; per-device data), not on point 1."

### S5. `logScanAttempt` telemetry silently 401s for exactly the users the doc says it profiles.

The doc's action table (line 594) correctly marks `logScanAttempt` as
**auth required**, and §`health-decisions-other` (line 1425) restates *"every
miss is stored"* as a data-licensing play.

But the client never escalates to a minted token for it:
`src/features/foods/conjureHealthDb.ts:64` — `const WRITE_ACTIONS = new Set(["submit"]);`
— so on mobile (where `getAccessToken()` is null by design) and for signed-out
desktop, `logScanAttempt` sends `Bearer <ANON>`, is refused
(`health-foods-db/index.ts:97`, anon satisfies neither auth path), and the client
swallows it (`conjureHealthDb.ts:88`).

Partly mitigated and worth saying: server-side `lookup()` writes its own scan
row for every barcode outcome including misses
(`health-foods-db/index.ts:229-234, 173-196`), so barcode misses *are* captured.
What is lost is the client-only terminal outcomes (`ai_label`, `ai_front`,
`usda`, `user_manual`, text queries).

**Should say:** note the split — server-side lookup telemetry is unconditional;
client-side `logScanAttempt` is auth-gated and drops silently on mobile and when
signed out.
